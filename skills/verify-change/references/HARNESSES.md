# Harness Selection

Load this reference when a material risk, unfamiliar quality harness, or unclear evidential boundary makes the smallest faithful portfolio difficult to select. Repository rules, specifications, architecture decisions, configured checks, and accepted thresholds remain authoritative.

## Select by claim and failure mode

Start with the claim, not a preferred tool. Choose an existing harness only when its observation and oracle can distinguish a failure of that claim within a known environment. Retain every applicable repository-required gate. Add another existing route only when it exposes a distinct material failure mode or reduces a named oracle, environment, or state-space weakness enough to justify its feedback cost. Do not invent a transient test, fuzzer, benchmark, generator, or reference implementation to close a project evidence gap; return that need as planned implementation work.

Run cheap diagnostic checks early when dependencies permit, but never substitute speed for fidelity. Prefer deterministic, local, narrowly diagnostic, machine-readable procedures for correction feedback. Preserve slower integration, specialist, or manual procedures when they alone exercise a material boundary. A required unreliable check remains unreliable evidence rather than a pass.

## General-purpose harnesses

| Harness family | Select when | Evidence supplied | Principal boundary and integrity check |
| --- | --- | --- | --- |
| Focused unit or component test | A stable observable boundary can exercise the changed behaviour economically. | The oracle accepted the exercised nominal, boundary, failure, or off-nominal examples. | It does not establish collaborations or environments outside the boundary. Reject tautological assertions, implementation-derived expectations, and hidden-structure coupling. |
| Executable acceptance or business example | A specification, acceptance criterion, or worked example is authoritative and precision benefits from execution. | The system produced the specified externally observable outcome for the examples. | Examples are not exhaustive. Keep business language tied to real production behaviour rather than step definitions that merely restate code. |
| Integration, contract, or system test | The change crosses a process, service, database, framework, protocol, hardware, or user-facing boundary. | Selected collaborators, interfaces, side effects, or end-to-end paths worked in the exercised configuration. | Contract tests do not prove provider internals or complete collaboration; isolated integration does not prove the deployed system. Record fakes, versions, topology, and omitted real boundaries. |
| Static type, lint, format, framework, or architecture check | The repository configures it, or a named structural or language rule governs the change. | The analysed source satisfied the configured rules in the inspected scope. | It proves only encoded and enabled rules. Inspect baselines, exclusions, suppressions, generated files, database freshness, and changed configuration. |
| Build or package check | Build inputs, dependencies, generated artefacts, packaging, or runtime compilation changed, or the repository requires it. | The declared inputs produced the expected artefact in the recorded environment. | One successful local build does not prove portability or reproducibility. Record dependency resolution, generated changes, environment, and artefact identity. |
| Broader regression suite | Changed behaviour or dependencies could affect established nearby or system behaviour, or the repository requires the suite. | Previously encoded expectations still passed across the suite's actual coverage. | Passing regressions inherit every oracle, exclusion, environment, and flakiness weakness in the suite. Distinguish focused new-behaviour evidence from pass-to-pass regression evidence. |
| Coverage analysis | A coverage gap could reveal changed code or a material path never exercised. | Which configured code, branches, or paths executed under the selected suite. | Coverage is not correctness or test effectiveness. Do not target a percentage without repository authority or treat execution as a discriminating oracle. |
| Changed-code mutation analysis | The sensitivity of changed or high-consequence tests is materially uncertain and existing infrastructure can run it economically. | Selected seeded faults were detected or survived within the mutation scope. | Survivors may be equivalent, irrelevant, unreachable, or genuine gaps. Record operator set, exclusions, timeouts, scope, and survivor appraisal; do not mandate whole-suite mutation. |
| Reproducible manual or specialist procedure | Automation cannot faithfully exercise a visual, physical, usability, domain, or contextual claim. | A named actor followed recorded steps against stated inputs and observed retained outcomes. | One observation may depend on competence and environment. Preserve steps, versions, data, screenshots or logs, expected result, actual result, and specialist limitations. |

## Risk-triggered specialist harnesses

| Material risk cue | Candidate existing evidence | What a clean result cannot establish |
| --- | --- | --- |
| Trust boundary, authentication or authorisation, sensitive data, cryptography, untrusted input, command or query construction, file handling, dependency or security configuration | Threat or attack-surface analysis, configured secret/dependency/SAST checks, security-focused tests, DAST, fuzzing, penetration procedure, qualified security review | One scanner or finite attack set cannot establish absence of vulnerabilities. Confirm scope, rule/database version, environment, permissions, suppressions, and untested threats. |
| User interface, semantic structure, keyboard or assistive-technology interaction, contrast, focus, motion, or accessibility requirement | Configured automated accessibility check plus interaction, browser, assistive-technology, or knowledgeable human evaluation as the claim requires | Automated rules cover only machine-detectable conditions; one browser, device, or evaluator does not establish conformance across the target population. |
| Hot path, algorithm, query, serialization, start-up, resource constraint, volume, latency, or throughput requirement | Focused benchmark, profile, load, stress, or soak procedure against an authoritative budget and representative workload | A result does not generalise beyond workload, environment, warm-up, sample size, variance, versions, and competing load. Compare a relevant baseline; do not infer improvement from one noisy run. |
| Supported runtime, browser, device, operating system, database, architecture, locale, time zone, or dependency matrix | Repository matrix, compatibility suite, representative build/run, or targeted manual procedure | Tested combinations do not cover omitted versions or interactions. Use the authoritative support matrix and record exact combinations. |
| Retry, timeout, failure recovery, partial outage, queue, distributed boundary, or degraded dependency | Fault injection, failure-path integration test, resilience procedure, recovery drill, or state-transition assertion | Synthetic faults may not match operational timing or correlated failures. Record injected conditions, recovery oracle, state cleanup, and unexercised modes. |
| Shared mutable state, parallel work, lock, transaction, async ordering, idempotency, or race-sensitive path | Deterministic schedule test when available, repeated stress with preserved seed and trace, invariant check, or focused concurrency procedure | Stress cannot prove absence of races; bounded schedule exploration cannot prove states beyond its model and bounds. Preserve the failing schedule or trace. |
| Schema, migration, backfill, serialization, data transformation, retention, destructive operation, or rollback promise | Representative production-shaped fixtures, forward and reverse migration where required, invariant/reconciliation queries, backup/restore or recovery procedure | Synthetic or sampled data may omit real distributions and invalid legacy states. Record scale, constraints, before/after invariants, failure recovery, and environment fidelity. |
| Environment-sensitive build, generated output, compiler/toolchain change, signed or distributed artefact | Clean build, repeated build under relevant declared variance, artefact comparison, provenance or signature check | Same-machine repetition does not establish reproducibility elsewhere. Record all material inputs, toolchain, environment variation, and comparison method. |
| High-consequence protocol, state machine, concurrency algorithm, or invariant already supported by project modelling infrastructure | Model checking, proof checking, symbolic execution, or other bounded formal analysis | The result applies to the stated model, assumptions, abstraction, and explored bounds; it does not prove model-to-code or environment correspondence without separate traceability. |

## Guard against self-confirming evidence

Inspect every changed test, snapshot, baseline, suppression, quality rule, ignore list, generator, fixture, benchmark, and harness script that participates in the verdict. Confirm that its change has specification or repository authority and that its oracle can disagree with the implementation. Treat a weakened or unexplained measurement path as a limitation even when its command is green, and leave independent acceptability judgement to code review.

For generated or sampled inputs, record the generator domain, distribution, seed, shrink or reduction result, and failing counterexample where applicable. For metrics, record the governing claim, measurement scope, interpretation, variance or threshold authority, and blind spots. Never combine unrelated evidence into a composite score that can hide a required failure or unsupported material risk.
