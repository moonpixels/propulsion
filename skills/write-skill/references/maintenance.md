# Maintain and release a skill

Start from the requested change and current evidence: task outcomes, failures, corrections, execution traces, references, callers, and compatibility. Preserve unrelated behaviour, but appraise existing rules against their contract or observed purpose. A complete replacement follows the newly confirmed contract rather than inheriting the old design.

## Diagnose before changing

Locate the failure at its actual layer: discovery, missing knowledge, procedure, tool support, source version, completion criterion, authority, or runtime presentation. Update the narrowest authoritative owner. Prefer a structural fix, tool check, schema, or clearer pointer when it removes the failure more reliably than another prose warning.

Scope a recurring correction to the condition where it applies. Resist turning a one-off incident into a global prohibition. Check callers and invocation routes before splitting, merging, renaming, or deleting a resource.

## Revise and prune

Retain concrete contracts, unfamiliar knowledge, exact formats, fragile-operation invariants, and meaningful failure alternatives. First question generic repetition, mandatory preparation, obsolete compensations, speculative edge cases, and compulsory review that changes no outcome.

Remove unused examples, orphaned resources, stale API details, and unnecessary router layers. Test changed behaviour; a shorter file alone is not an improvement.

Apply targeted paired comparisons and rerun affected regression cases. Repeat broader evaluation when model, effort, client, permissions, tools, domain contracts, or intended task scope change. Recalibrate checking and persistence for the actual configuration instead of assuming newer models always need less guidance.

## Release

Validate packaging and destination loading, run applicable project checks, and publish or install only within the requested authority. Treat a release as a **reproducible dependency**: retain its bundle revision, important resource versions, compatibility assumptions, evaluation configuration, and relevant results together. Pin released versions where the deployment supports versioning.

Keep a small author-maintenance record linking consequential rules to their contractual requirement or failure case and the evidence used to retain them. Use existing version history or maintenance records where sufficient. Keep cases and evaluation history outside the runtime instructions, and avoid adding a README, changelog, duplicated quick reference, or empty resource tree without a concrete need.

Retire a skill when its distinct capability is no longer useful, its knowledge is reliably handled without it, or another maintained authority owns the contract. Resolve callers and discovery entries before removal. Return changed paths, evidence, compatibility changes, and unresolved uncertainty.
